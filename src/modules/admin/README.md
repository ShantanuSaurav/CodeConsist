# modules/admin

**Owns:** the administrator console at `/admin`: a separate sign-in (Admin User ID + password, never a learner account), the admin session token (`STORAGE_KEYS.adminToken`), and the pages for users, billing, language tracks, stages, challenges, analytics, the learning rules (Rules & rewards), the audit log, the optional Microsoft Excel mirror and credential changes.

**Rules & rewards (`pages/AdminRules.tsx`, `/admin/rules/:sectionId`, nav group "Learning").** Every learning rule - XP and scoring, the level curve and rank titles, streak and time-zone rules, data limits - edited in one place without a redeploy (docs/adr/0008). Defaults live in code (`src/platform/settings/defaults.ts`); the server stores only what an admin changed, with a revision number.

- **One page, generated.** The section list and every field come from `SECTION_META` / `SETTING_META` in `src/platform/settings/meta.ts` (`components/settings/sections.ts`, `GenericSection.tsx`, `fields.tsx`), so a key is editable the day it is added. A section that needs more than fields gets a custom component: `LevelsSection.tsx` adds "Generate curve" (base × (L−1) × L for N levels, then a step), the number of learners whose level the unsaved curve would change (from `GET /settings/context`'s `levels.learnerXp`), and a warning when the top rank is out of reach of all the XP the content is worth.
- **Each field** shows its help, "Default: X", Reset when overridden (sends `null`), "from .env" when an environment variable supplies it, and the problem found at its path. Each section shows "Using defaults" or "N changes" and **Reset section** (behind a confirm, sends `{ [section]: null }`).
- **Saving.** Nothing is sent until Save. The edits are checked locally with the same zod schema the server uses (`@/platform/settings/schema` - fine here, the admin chunk is lazy), then sent as a sparse `PUT /api/admin/settings { revision, patch }`. A 409 means someone saved first: "Changed elsewhere - reload", with the edits kept. A 422 carries `issues` tied to paths, shown under their fields. Every save is audited as `settings.update` with each changed path's old and new value. The server applies a change to the very next request; open learner tabs refetch within one health probe (30 s).
- **Stored values the server had to ignore** (a section that stopped validating after a code change runs on its defaults) are listed at the top of the page.
- The URL is `/admin/rules`, not `/admin/settings/...`: `/admin/settings/security` is the admin's own credentials page.

**Analytics: Most missed.** Built from recorded wrong answers (`db.activity`, written by `POST /api/activity/misses` and the guest merge), never from `attempts` (written only on a solve, so the old list was always empty). Each row: how many learners missed it out of those who tried, the miss rate, total wrong answers (and how many ended with the answer shown), and the most common wrong answer. A question is listed once `retention.mostMissedMinLearners` learners have missed it. Selecting a row opens the answer distribution (top 10) and the latest 20 wrong answers - answers only, never who gave them (`GET /analytics/challenges/:id/misses`).

**Users: Learning.** The activity button on a user row opens their time zone, the last 14 weeks as a heatmap and the questions they miss most (`GET /users/:id/learning`). The "Setup & test-outs" tab (Phase 5, `components/UserSetupPanel.tsx`) shows whether the learner finished or dismissed the first-run setup and what they answered, the stages they tested out of, their newest 20 test-outs and placements, and **Clear test-out cooldowns** (`POST /users/:id/assessments/clear-cooldown`, audited as `assessment.cooldown.clear`): everything they started before now stops counting towards their limits and waits; nothing they passed changes.

**Onboarding, placement and test-out (Phase 5).** Three sections of Rules & rewards with their own pages: `/admin/rules/onboarding` (nav group "Learning") shows a live preview of the first-run setup drawn with the learner's own primitives (`components/settings/OnboardingSection.tsx`); `/admin/rules/placement` and `/admin/rules/testOut` (`components/settings/AssessmentSections.tsx`) say how many runs a pass mark allows and list every track's stages - which a placement may test, which can be tested out of - with whether this server can check each stage test itself and a link that opens it in the question wizard (`/admin/challenges?stage=…&edit=…`). The stage-order gates and their counters are on Limits & access. Analytics has an "Onboarding and placement" card (`GET /analytics/onboarding`; accounts only).

**Weekly league (`pages/AdminLeagues.tsx`, `/admin/leagues`, nav group "Learning"; Phase 6, docs/adr/0013).** The current week's standings (`GET /leagues/weeks/:id`): each learner's week XP, raw league XP, the reset baseline, time zone, join time, exclusion and - with tiers on - group, tier and whether they are in line to move up or down. Row actions **Exclude** (with an optional reason) / **Reinstate** (`POST /leagues/weeks/:id/exclude`) and, with tiers on, **Move tier** (`PATCH /leagues/members/:userId`; applies from the next week). Week actions **Close week now** and **Reset week XP** (`POST /leagues/weeks/:id/close` / `reset`), each confirmed by typing the week id (the server refuses the call without it, and a closed week with 409). A table of the weeks before (`GET /leagues/weeks`) opens any one's results. Every change is audited (`league.week.close`, `league.week.reset`, `league.member.exclude` / `reinstate`, `league.member.tier`). The league's rules are the `league` section of Rules & rewards (`/admin/rules/league`); last week's banner texts are in the `reminders` section. The Users drawer shows the learner's place this week and their tier (`league` in `GET /users/:id/learning`).

**Site copy (`/admin/rules/copy`, nav group "Content").** The `copy` section of the settings store: every offline and error message, the sync labels, the Playground description, the landing page lines, the meta description, the limit and premium messages and the not-found and crash screens. `components/settings/CopySection.tsx` groups them by where they appear; each field shows its allowed `{tokens}` as chips and a preview filled with the real content counts from `GET /settings/context`. A text may use only its own tokens and at most 300 characters (checked by the shared schema). Learners get it with the rest of `GET /api/settings`; the server uses the same texts for its 429, busy and premium answers (`copyText` in `server/settings.js`).

**Limits & access (`/admin/rules/access`, nav group "Operations").** The admin-only `access` section: rate limits per bucket and their mode, code-runner capacity, trusted proxy hops (`TRUST_PROXY_HOPS` in `.env` sets the default), CORS mode and extra origins, the server-side premium lock (`enforce` / `log`, the emergency switch) and the reset-link lifetime. `components/settings/AccessSection.tsx` puts a live card above the form (`GET /access/status`): your own request as the server sees it (socket, `X-Forwarded-For`, the derived address - check the hops against it), every bucket's refusals and busiest keys with **Unblock** (`POST /access/rate-limits/reset`, audited as `security.rate-limit.reset`), the code-runner slots, the CORS allow-list with each origin's source and the foreign origins recorded, and the premium lock's blocks. All of that is in memory on the server; a restart clears it. The existing **Security** page is the admin's own sign-in and stays separate. Billing shows a read-only "Server-side premium lock" line.

**Users: Reset link.** The key button on a user row opens `components/PasswordResetDialog.tsx`: issue a one-time link (`POST /users/:id/password-reset`), shown once with Copy - the server keeps only its SHA-256 and never audits the token - list earlier links with their status and revoke a live one. Issuing a new link withdraws the open one. The learner opens `/reset-password#token=...`, sets a password and is signed in; every other session of the account is signed out. The table shows an "Active reset link" badge while one is live.

**Public API (`index.ts`):** `AdminApp` - the whole `/admin/*` route tree with its own `AdminAuthProvider`. The app mounts it lazily, so learners never download it.

**Talks to:** `/api/admin-auth/*` and `/api/admin/*` only (`services/adminApi.ts`). Every one of those routes is independently gated server-side by `requireAdminAuth` (`server/admin-auth.js`), which verifies the bearer token against the live admin record on every request. This module could be deleted and a learner's token would still get a 401 from all of them.

**Three states of question.** *Authored* ones live in `src/modules/challenges/content` and go through `npm run check` (which executes every solution). *Edited here* (`modified: true`) is an authored id whose full replacement was saved from the console: the server stores it in `customChallenges` in `server/data/db.json` under the same id, learners see the replacement in the authored position (so it keeps its stage - the server refuses a stage move), and the row's "Put the original back" (`POST /content/challenges/:id/revert`) deletes the replacement again. *Written here* (`custom: true`) is a question whose id is not in the authored bank at all - created with the "New question" wizard, appended after the authored lessons of its stage, and deletable outright. All three are edited with the same wizard (`components/QuestionWizard.tsx`: type first, then a per-type form with every field - options, blanks, steps, test cases, and worked examples for a stage test); the server (`server/custom-challenges.js` + the zod `ChallengeSchema` compiled at boot) validates every save, executes a coding question's solution against its test cases (and checks a `debug` starter fails), holds a stage test to its shape, and keeps an authored question's Learn-mode `concept` untouched. Removing a question from a stage (a reversible hide) works on all three and is a `contentOverrides` entry in the same db.json, merged by `server/content.js`.

**AI question assistant.** The "AI new question" button on the Challenges page opens `components/AiQuestionAssistant.tsx`: the admin picks a type, describes the question in plain words, and Gemini writes it out in full, names the stage it fits best (with a confidence and alternatives), and compares it with every question already in the bank - each overlapping one is labelled duplicate / similar / distinct and the verdict (push it / push with care / don't push) is computed from those labels, so a duplicate can never be saved from the assistant. A second tab asks Gemini for new question ideas for a stage, each marked New or Overlaps "<title>"; "Write this one" feeds an idea straight back into the first tab. Everything talks to `/api/admin/ai/*` (`server/ai.js`, `server/ai-questions.js`): the `GEMINI_API_KEY` is read only by the API server and is never bundled or sent to the browser, and what goes to Google is the admin's own words plus the titles and prompts of existing questions for the duplicate check - never learner data or credentials. Every AI draft still goes through the same validation and solution execution as the wizard (`validateQuestion` before it is shown, and the normal create route when it is saved); "Review in wizard" opens it in `QuestionWizard` (its `draft` prop) for edits by hand. With no key set, the drawer explains what to add to `.env` and stays switched off; the Dashboard's Integrations card shows the same status.

**Billing (`pages/AdminBilling.tsx`, `/admin/billing`).** What is sold is fixed - a lifetime licence, a track, a single premium stage, or a verified certificate for a finished track - as one-time purchases in INR through Razorpay; there is no subscription. Everything on the page talks to `/api/admin/billing/*` (`server/admin.js`, backed by `server/billing.js`) and every amount crosses the wire in paise; the page converts to and from rupees in one place at its top. In order:

- **Mode banner.** `RAZORPAY_KEY_ID` + `RAZORPAY_KEY_SECRET` set in `.env` = live: learners pay through Razorpay's checkout and the server verifies the signature (`POST /api/billing/orders/:id/confirm`) or the webhook (`POST /api/billing/webhook`, `RAZORPAY_WEBHOOK_SECRET`) before anything unlocks. Unset = **test mode**: learners see a clearly labelled "Complete test payment" step (`/test-complete`, refused once real keys exist), no money moves, and the Dashboard's Integrations card says so.
- **Prices** (`GET`/`PUT /billing/pricing`). Lifetime, per track, per premium stage (only stages marked Premium under Stages appear), certificate per track. A blank/"Reset" puts a key back to the code default (`DEFAULT_PRICES` in `server/billing.js`); only changed keys are sent, a value equal to the default goes up as `null`; ₹0 is allowed and means free. Audited as `billing.pricing.update`.
- **Grant access** (`POST /billing/grant`). For payments taken outside Razorpay: pick a user, a product, write a note, optionally the name to print on a certificate. The server runs the same `canPurchase` rules a learner's own order does (already owns it, certificate not yet earned...) and records a paid order with provider `admin` and ₹0. Audited as `billing.grant`.
- **Orders** (`GET /billing/orders?status=&q=`), newest first with a status filter. **Revoke** (`POST /billing/orders/:id/revoke`, behind a confirm) sets the order to `revoked`: the access disappears from the learner's `unlockedStages` on their next account refresh, and a certificate the order issued shows as revoked at `/verify/<id>`. It does not refund anything in Razorpay. Audited as `billing.revoke`.
- **Certificates** (`GET /billing/certificates`): every issued certificate, the name printed on it, the account, the track, and whether it is still valid.

How entitlements are computed (server-side, `entitlementsFor` in `server/billing.js`): `lifetime` = the legacy per-user Premium toggle on the Users page **or** a paid `lifetime` order; `stageIds`/`trackIds` from paid stage/track orders, with tracks expanded against the *current* track list so a stage added to a track later is covered; a premium stage is open when `lifetime || unlockedStageIds.has(stage.id)`. The learner app only ever mirrors `publicUser.isPremium` / `publicUser.unlockedStages` - nothing in the browser can grant itself anything. The Dashboard's Revenue card counts paid orders and sums their amounts (test-mode orders are recorded at list price so the flow can be checked end to end).

**Does not own:** learner progress, grading, XP (`platform/session`, `server/progress-routes.js`), the rules themselves (`platform/settings`, `server/settings.js`) or the activity log (`platform/activity`, `server/activity.js`) - it edits and reads them through `/api/admin/*`.
